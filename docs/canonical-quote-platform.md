# canonical.plus quote platform: repository, dependency, and rollout map

## Purpose

This document is the organization-level source for the signed-in compliance
quote platform spanning `canonical.plus`, `app.canonical.plus`, and
`api.canonical.plus`. It defines repository ownership, dependency direction,
GitHub/Linear planning boundaries, release order, and the production
certification gates.

The platform must preserve these public boundaries:

| Surface | Responsibility | Authentication |
| --- | --- | --- |
| `canonical.plus` | Marketing site and quote/sign-in calls to action | Public |
| `app.canonical.plus/u/quote` | Maud/HTMX signed-in quote workspace | Host-only Shared Auth browser cookie, independently verified by the Rust origin |
| `app.canonical.plus/shared-auth/*` | First-party magic-link browser ceremony for the Canonical realm | Canonical-specific issuer, audience, Supabase project, signing/sealing keys, Redis namespace, and cookies |
| `app.canonical.plus/api/v1/quotes*` | Browser REST recovery and WebSocket status | Browser cookie plus Origin/CSRF where applicable |
| `api.canonical.plus/api/v1/quotes*` | SDK/CLI REST and WebSocket API | Shared Auth bearer token, independently verified by the Rust API origin |

Cloudflare is a routing and defense-in-depth layer. It is never the sole
authorization authority.

## Repository ownership

### Contracts and reusable code

| Repository | Owns | May depend on |
| --- | --- | --- |
| `canonical-interfaces` | Versioned JSON schemas and generated language contracts for quote requests, responses, errors, status events, and WebSocket messages | Nothing product-specific |
| `canonical-lib` | Reusable domain validation, framework identifiers, context composition, and non-I/O business rules | `canonical-interfaces` |
| `canonical-clients` | Generated and handwritten SDK layers for Rust, TypeScript, Go, Dart, WASM, Gleam, Erlang, and other supported clients | `canonical-interfaces`, optionally `canonical-lib` where language-compatible |
| `canonical-cli` | User-facing command-line workflows and `flags-2-env` integration | `canonical-interfaces`, `canonical-lib`, `canonical-clients` |

`canonical-interfaces` is the contract authority. A service or client must not
publish a second incompatible quote model under the same version.

### Applications and deployment composition

| Repository | Owns | Notes |
| --- | --- | --- |
| `canonical-web-server.rs` | `canonical-web-server` browser binary and, until a deliberate split is completed, the standalone `canonical-api-server` Rust binary | Maud, Axum, SeaORM, Supabase integration, HTMX, REST, and WebSockets share one reviewed security/domain implementation |
| `canonical-flutter` | Flutter application surfaces | Consumes generated clients; does not duplicate REST/WS schemas |
| `canonical-infra` | Canonical-specific composition for DNS, Worker route declarations, and provider-neutral deployment documentation | Shared Auth core Worker logic remains in `shared-auth-infra`; Canonical wrappers/configuration may be referenced or generated here without copying security logic |
| `canonical-monorepo` | Exact source inventory and the only Canonical image-release authority | Pins deployable repositories and publishes web, API, and revoker images from one tested SHA |
| `ORESoftware/k8s-cluster` | Argo CD desired state, immutable digest promotion, Secrets Manager references, Ingress, Services, NetworkPolicies, and rollback | Argo CD is the only Kubernetes writer |

A separate `canonical-api-server.rs` repository should be created only after a
reviewed extraction plan preserves one source for authentication, RLS, quote
contracts, and WebSocket behavior. The current standalone binary is already a
separate process and image; a repository split is not required for the
`api.canonical.plus` host boundary.

## Zed package and submodule rules

Use one dependency transport per repository edge:

1. `.zpkg.toml` is authoritative for contracts, reusable libraries, clients,
   CLIs, tooling, and generated-source inputs.
2. Git submodules are limited to exact deployable source inventory in
   `canonical-monorepo` and other repositories whose explicit purpose is
   composing/test-building multiple repositories at one SHA.
3. The same dependency must never appear in both `.zpkg.toml` and `.gitmodules`
   in one consumer repository.
4. `.zpkg.lock` is generated by Zed tooling. Do not hand-author synthetic lock
   entries or commit floating branch references as resolved dependencies.
5. Application repositories consume published/generated interfaces through
   Zed package materialization. They do not copy schemas into private models
   without a compatibility test.
6. Submodule updates are reviewed as release inputs: the parent CI must test
   the exact pinned commit before any image can be published.

Expected logical direction:

```text
canonical-interfaces
        ↓
   canonical-lib
      ↙     ↘
canonical-clients  canonical-web-server.rs
        ↓                    ↓
   canonical-cli       canonical-monorepo
                              ↓
                    immutable GHCR images
                              ↓
                 ORESoftware/k8s-cluster
```

## Contract release gate

`canonical-interfaces` already contains a quote schema and generated Rust
bindings, while the current Rust quote implementation uses a different request,
response, framework, and status-event shape. This mismatch is a release blocker
for the cross-language SDK/CLI surface.

Before calling the API contract stable:

- choose and version one canonical request/response/status schema;
- cover SOC 2, NIST, HIPAA, ISO 27001, FedRAMP, and PCI DSS identifiers without
  ambiguous aliases;
- generate Rust and client bindings from that schema;
- make the web/API service consume or mechanically prove compatibility with the
  generated Rust types;
- add golden JSON fixtures for REST requests, REST responses, errors, and every
  WebSocket event;
- add backward/forward compatibility tests and an explicit versioning policy;
- update `.zpkg.toml` dependencies without dual-registering any submodule.

Until this gate passes, browser functionality may be evaluated as an
application slice, but generated external clients must be marked pre-stable.

## Release and activation order

The safe dependency order is:

1. Reconcile the quote contract in `canonical-interfaces`, regenerate clients,
   and update the Rust application compatibility tests.
2. Restore executable CI for the private Shared Auth repositories or run an
   equivalent independent matrix with retained evidence.
3. Merge and release the Canonical Shared Auth server realm and first-party
   `/shared-auth/*` origin route.
4. Merge the Canonical Cloudflare edge configuration after Node tests and a
   Wrangler dry deploy pass.
5. Merge `canonical-web-server.rs` only when the exact current head passes Rust,
   browser, RLS, schema, dependency, and all three container-target checks.
6. Pin that exact merge in `canonical-monorepo`; publish and attest web, API,
   and revoker images from one successful monorepo SHA.
7. Promote all three immutable digests atomically in
   `ORESoftware/k8s-cluster`; never deploy the placeholder API tag.
8. Provision isolated Shared Auth, web, API, revoker, database, Supabase, Redis,
   Gemini, registry, webhook, signing, and sealing secrets.
9. Apply schema/runtime-role changes with the privileged migration identity;
   no long-lived pod receives a migration URL or Supabase service-role key.
10. Attach the exact Cloudflare Worker routes and enable proxied DNS only after
    origin health and TLS checks succeed.
11. Certify login, sealed return state, CSRF rejection, revocation, owner
    isolation, quote submission, Gemini failure handling, REST recovery, and
    WebSocket reconnect/status behavior in the deployed environment.

## GitHub Projects structure

The Canonical Cloud organization should maintain one project named
**Canonical Cloud Quote Platform**. Recommended fields:

- **Status:** Backlog, Ready, In progress, In review, Blocked, Ready to deploy,
  Certifying, Done.
- **Workstream:** Contract, Identity, Web, API, AI analysis, Edge, Data,
  Release, GitOps, Certification.
- **Repository:** the owning repository, not the umbrella organization.
- **Environment:** Local, CI, Remote dev, Staging, Production.
- **Release gate:** Contract, Security, Test, Artifact, Secret, Origin, Edge,
  Certification.
- **Risk:** Critical, High, Medium, Low.

Every cross-repository issue must name one owning repository and link dependent
issues rather than assigning the same implementation to multiple repositories.
PRs should be linked to the corresponding issue and carry the exact dependency
order above.

## Linear mirror

Mirror the GitHub project in the ORESoftware Linear team as
**Canonical Cloud Quote Platform**. Linear is the planning/coordination view;
GitHub remains the code-review and release-evidence view.

Minimum P0 issues:

1. Reconcile `canonical-interfaces` with Rust REST and WebSocket quote contracts.
2. Certify and release the Canonical Shared Auth realm and first-party Ingress.
3. Certify the app/API Cloudflare Worker and attach exact routes.
4. Publish and attest the three-image monorepo release.
5. Provision Canonical-only Supabase, RDS, Redis, Gemini, signing, sealing,
   webhook, introspection, and registry secrets.
6. Promote exact digests and run the deployed end-to-end certification matrix.

Use dependency links so image release is blocked by the application merge,
GitOps promotion is blocked by image publication, and production certification
is blocked by identity, edge, data, secret, and origin readiness.

## Production invariants

- Browser cookies are host-only to `app.canonical.plus`.
- `api.canonical.plus` accepts Shared Auth bearer credentials, not browser
  cookies or legacy Supabase headers.
- The Rust origin independently verifies credentials and revocation.
- All quote rows are owner-scoped under forced PostgreSQL RLS.
- PostgreSQL is authoritative; WebSockets are notifications and REST is the
  recovery path.
- Gemini output is preliminary analysis for human review, not an audit opinion,
  certification, attestation, or legal conclusion.
- Only the API workload receives `GEMINI_API_KEY`.
- Every deployed image is an immutable digest from the same tested monorepo SHA.
- Argo CD is the only Kubernetes writer.
- Secrets, credentials, PATs, authorization codes, and raw tokens never enter
  commits, PR bodies, issue descriptions, logs, URLs, or generated artifacts.
